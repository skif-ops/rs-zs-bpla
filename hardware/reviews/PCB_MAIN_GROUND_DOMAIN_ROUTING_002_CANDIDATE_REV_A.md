## 1. Что изменено

Изменена только медь земли. Netlist, назначения выводов, размещение, контур, RF-запреты, правила
площадок H1–H4 и соединения доменов не менялись. Генератор проверяет, что вне заявленной дельты
кандидат совпадает с базой байт в байт. Для этого из кандидата убираются добавленные строки,
возвращается прежний блок зоны, и результат сравнивается с базой.

| Элемент | База | Кандидат |
|---|---|---|
| In4.Cu `GND_MODEM` | одна зона 5238 мм²: вся плата, кроме GNSS/LoRa/BLE/аудио | две зоны с приоритетом 1: 2445 мм² (модемный регион) и 5,3 мм² (площадка земли TP_CELL_DBG) |
| In4.Cu `GND_DIGITAL` | нет | одна зона по цифровому контуру In1 (6941 мм², фактически 5489 мм² вне модемного региона), приоритет 0 |
| Via `GND_DIGITAL` 0,5/0,3 | — | +15 сшивающих |
| Дорожка `GND_MODEM` In3.Cu 0,3 мм | — | +1 связка, 4 сегмента, 12,61 мм |
| In1.Cu, In2.Cu, F.Cu, B.Cu | — | без изменений |

После заливки основной модемный кусок In4 соединён 94 via `GND_MODEM`, цифровой — 144 via
`GND_DIGITAL`. Островок 5,2 мм² держится своим via и связкой по In3.

## 2. Правила модемного региона In4

Регион получен из платы и авторитетов, вручную не рисовался.

- **Состав.** Регион объединяет:
  - `ZONE_CELL` (x 10…36, y 34…74);
  - оболочки площадок (+0,6 мм) всех компонентов, у которых есть площадка на `GND_MODEM` или на
    цепи с `Reference_Domain = GND_MODEM`; у J_PWR — только модемные контакты;
  - все проложенные модемные дорожки и via (+1,0 мм);
  - коридоры будущих модемных маршрутов (+1,5 мм) — минимальное остовное дерево между площадками
    каждой модемной цепи.
- **Замыкание и обрезка.** Регион замкнут на 1,5 мм и обрезан прежним контуром `GND_MODEM` на In4.
  Поэтому GNSS, LoRa, корпус BLE и тихая аудиозона остались без модемной меди, как и раньше.
- **Приоритет цифры.**
  - Оболочка площадок U1 (MCU) +1,0 мм остаётся цифровой.
  - Вокруг каждой проложенной цифровой дорожки B.Cu сохраняется 0,8 мм цифровой опоры.
  - Исключение — островки 0,35 мм вокруг модемной меди, которая физически стоит там. Это
    контрольные площадки TP_CELL_DBG снизу под U1; их размещение по условию ECO не меняется.
- **Очистка.** Перешейки уже 0,4 мм удаляются. Модемный кусок остаётся, только если касается меди
  `GND_MODEM`; иначе это мёртвая медь, а не опора.

В результате `GND_MODEM` на In4 остаётся под:
- сотовой зоной с модемом U8;
- левой полосой вдоль края, где уже проложен USB-маршрут модема к контрольным точкам;
- J_PWR и цепями 3V8 модема;
- U16, U13, SIM1 (J6), SIM2 (J7, U15) и коридором между ними;
- восточной полосой x 37…42 (C42, D10, FB1, U27).

Остальная площадь In4 — `GND_DIGITAL`.

## 3. Карта «цепь/домен → слой → опорная медь»

Опорный слой: F.Cu → In1.Cu; B.Cu → In4.Cu (0,0994 мм по JLC06161H-3313).
In2.Cu — слой плоскости `GND_MIC`, не сигнальный. In3.Cu по ревизии не является цифровым: до
In2/`GND_MIC` 0,1088 мм, до In4 0,55 мм.

Доля длины проложенных дорожек над медью своего домена. Считается по залитой меди KiCad 9.0.9;
контуры зон приведены для сравнения.

| Слой, домен | Длина, мм | База | Кандидат | По контурам зон |
|---|---:|---:|---:|---:|
| B.Cu, `GND_DIGITAL` | 67,8 | **0 %** | **94,6 %** | 100 % |
| B.Cu, `GND_MODEM` | 148,9 | 99,4 % | 99,4 % | 100 % |
| F.Cu, `GND_DIGITAL` | 238,0 | 93,8 % | 93,8 % | 100 % |
| F.Cu, `GND_MODEM` | 66,7 | 91,5 % | 91,5 % | 91,5 % |
| F.Cu, интерфейс DIGITAL↔MODEM | 41,0 | 0 % | 0 % | — (п. 5) |
| In2.Cu, `GND_DIGITAL` | 157,4 | 0 % | 0 % | — (п. 6) |

Разница между заливкой и контурами у B.Cu и F.Cu — вырезы заливки вокруг via и площадок других
цепей, а не разрывы плоскости. Для F.Cu она одинакова в базе и кандидате. Если в местах антипадов
нужна отдельная оценка, её можно сделать по `REFERENCE_MAP.json` → `continuity_by_net_layer`.

5,7 мм модемных дорожек F.Cu лежат вне модемной зоны In1: это выводы USB модема `CELL_USB_DM_TP`
(2,62 мм) и `CELL_USB_DP_TP` (3,08 мм) у x 8…10, до перехода на B.Cu. Так было и в базе, данный ECO
их не затрагивает.

Полная карта по каждой цепи и слою: `REFERENCE_MAP.json`.

## 4. Переходы слоёв и сшивка

Для каждого сигнального via цифрового домена проверено расстояние до ближайшего via `GND_DIGITAL`.
Цель — не больше 1,5 мм, радиус поиска 2,5 мм. Новый via ставится, только если он ближе
существующего. Место выбирается с зазором 0,2 мм до меди на всех шести слоях, 0,25 мм между
отверстиями, вне площадок и правил H1–H4, внутри новой цифровой меди In4.

| Результат | Переходов |
|---|---:|
| Via `GND_DIGITAL` уже ближе 1,5 мм | 9 |
| Добавлен сшивающий via, итог ≤ 1,5 мм | 11 |
| Добавлен via, стало ближе, но > 1,5 мм (1,56…2,11 мм) | 4 |
| Места ближе существующего via нет | 7 |

Семь переходов без места: BOOT0 (49,2; 21,2), NOR_CLK_U1 (53,0; 18,0), NOR_IO3_U1 (54,7; 36,6),
NOR_IO0_U1 (57,6; 20,1) и (58,7; 21,7), NOR_IO0_U2 (59,9; 21,2), NOR_IO2_U2 (62,0; 22,1). Все они в
плотной зоне у MCU, текущие расстояния 1,65…3,40 мм. Пять из семи — на цепях, у которых есть участки
на In2/In3 (п. 6), поэтому решение по ним связано с решением по внутренним слоям.

Модемные переходы USB модема (8,2; 50,2) и (8,7; 52,6) имеют via `GND_MODEM` в 1,04 и 0,87 мм.

Поштучный список: `SPEC.json` → `stitching_report`.

## 5. Междоменные интерфейсы — проверяются отдельно

Переразметка In4 их не исправляет, и они не объявляются исправленными.

- **DIGITAL↔MODEM**, 11 цепей: `CELL_*_U16`, `CELL_PWRKEY_CMD`, `CELL_RESET_N_CMD`, `SIM1_DET`,
  `SIM2_DET`, `SIM_MUX_EN`, `SIM_MUX_SEL`. Проложен только `CELL_RX_U16`: 41 мм по F.Cu от U16 к U1.
  Эти цепи пересекают границу доменов у сдвигателя уровней U16 и мультиплексора U13. Опора
  меняется на границе. Домены соединены только перемычками NT1–NT3 на PCB-PWR через J_PWR; этот путь
  не изменён.
- **DIGITAL↔MIC**, 7 цепей: `PDM_*`, `AAD_CFG_1V8_FANOUT`, `MIC_WAKE_OR_1V8`. Пока не проложены.
  Аудиозона на In4 была без модема и осталась без модема; теперь под ней `GND_DIGITAL`.

## 6. Находка вне объёма ECO: трассы на In2 и In3

В рабочей плате уже проложено (наследие принятого ECO-002 R8 и маршрутизации OctoSPI):

| Слой | Цепи | Длина, мм |
|---|---|---:|
| In2.Cu (слой плоскости `GND_MIC`) | `NOR_IO0_U1` 35,1; `SD_D2_U1` 32,8; `EN_MODEM` 40,7; `NOR_IO1_U1` 20,3; `NOR_IO3_U2` 15,4; `NOR_IO1_U2` 13,1 | 157,4 |
| In3.Cu | `NOR_IO2_U1` 35,5; `NOR_IO2_U2` 22,8; `NOR_CLK_U1` 21,3; `NOR_CLK_U2` 16,7; `NOR_IO0_U2` 16,4 | 112,7 |

Эти трассы не имеют цифровой опоры. На In2 они ещё и прорезают плоскость `GND_MIC`. Это прямо
противоречит ограничению In3 из ревизии: до отдельного обоснования цифровые трассы вести по F.Cu над
In1 и по B.Cu над цифровыми областями In4.

Этот ECO их не трогает — геометрия сохранена побайтно. Нужно отдельное решение ревьюера:
- (а) перетрассировать OctoSPI/SD/`EN_MODEM` на F.Cu/B.Cu отдельным ECO (после 002 на B.Cu у MCU
  появилась цифровая опора);
- (б) согласовать расширение ECO на In2/стек.

## 7. Связка `GND_MODEM` по In3

После разделения площадка земли TP_CELL_DBG (контрольные площадки UART, USB BOOT и `VDD_EXT` модема
снизу под U1) вместе с via (56,23; 29,10) оказалась отрезана от основной модемной меди. Вести
модемную полосу по In4 под MCU нельзя: она разрезала бы цифровую опору под LQFP-100. Без связки
прогон 1 дал +1 неразведённое соединение.

Связка — дорожка `GND_MODEM` 0,3 мм по In3.Cu, 4 сегмента, 12,61 мм, от via (56,23; 29,10) до via
`GND_MODEM` (60,10; 17,23) в коридоре SIM2. Путь найден A* с зазором 0,2 мм до всей меди In3,
включая трассы OctoSPI и новые via. Минимальный зазор до нового via — 0,204 мм. Это земляной
проводник, а не сигнал, поэтому ограничение на цифровые сигналы по In3 его не касается. Ревьюер
может выбрать другое решение: переставить TP_CELL_DBG отдельным изменением размещения или вести
землю этих площадок при трассировке.

## 9. Регрессии ранее принятых маршрутов

Все сигнальные дорожки и via базы сохранены побайтно.

- **RF** (`CELL_RF`, `CELL_RF_ANT`; F.Cu над модемной In1): опора не менялась.
- **USB модема** (`CELL_USB_*_TP`, B.Cu 149 мм): остаётся над `GND_MODEM` — 99,4 % по заливке,
  100 % по контурам.
- **OctoSPI и SD на B.Cu** (`NOR_IO3_U1`, `NOR_IO3_U2`, `NOR_IO1_U2`, `BOOT0`): были над модемной
  опорой или без опоры, теперь над цифровой, 93–95 % по заливке. Участки на In2/In3 — п. 6.
- **Правила H1–H4 и антенный запрет BLE:** не менялись, заливка их соблюдает.

## 10. Запрос решения

Требуется отдельное решение ревьюера на конкретный SHA кандидата
`c168f5f2418776bf037598e856f4920d02c30c9702ab0a4c485146d93b17c536`:

- `ACCEPT_GROUND_DOMAIN_ROUTING_002` — разрешает только применение этого кандидата к рабочей плате.
  Применение оформляется отдельной записью со сверкой SHA.
