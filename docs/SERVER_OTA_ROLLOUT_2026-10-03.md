# Сервер «Мухоед»: раскатка прошивки станциям — canary, волны, пауза, возврат, журнал (2026-10-03)

Пункт 6 аудита выпуска (`server/EVT_PRE_20_RELEASE_AUDIT.md`: «нет OTA repository, canary rollout, pause и rollback
audit») и строка выпускного gate «журнал отката OTA». Хранилище выпусков и обновление одной станции по команде были
(аддендум F: `python -m pki.cli fw-sign`, `POST /api/v1/stations/{id}/firmware-update`); этим документом добавлена
раскатка выпуска на группу станций с canary-волной, паузой по отказам, отменой, возвратом и журналом каждого шага.

## 1. Как идёт раскатка

`station/rollout.py`. Раскатка — выпуск из хранилища (`version`), набор станций и правила:

- **canary-волна**: станции `canary` (или первые `canary_count` из списка, по умолчанию одна) получают команду
  первыми; остальные («основная волна») — только когда каждая canary-станция *подтвердила* выпуск: её heartbeat
  сообщает новую версию работающей (`fw_version`) и не на испытании (`fw_state` IDLE, аддендум F §3);
- **в полёте** одновременно не больше `max_in_flight` станций (по умолчанию 10, `ZS_ROLLOUT_MAX_IN_FLIGHT`):
  скомандованных, загрузивших или на испытании; следующие получают команду по мере подтверждений;
- **пауза по отказам**: отказ — ACK не `OK` (REJECTED/FAILED с кодом аддендума F) или heartbeat, в котором станция
  сама откатила выпуск (`fw_state` ROLLED_BACK, `fw_other_version` = выпуск: загрузочный страж после трёх неудачных
  стартов). После `max_failures` отказов (по умолчанию 1, `ZS_ROLLOUT_MAX_FAILURES`) раскатка останавливается сама,
  причина — в записи раскатки и в журнале; дальше инженер продолжает (`resume`: отказы к этому моменту считаются
  увиденными, пауза повторится после `max_failures` новых), отменяет (`cancel`) или возвращает (`revert`);
- **недоступные станции**: команда живёт 15 минут (TTL команд); станция, не ответившая за это время, получает её
  снова, до `ZS_ROLLOUT_COMMAND_ATTEMPTS` раз (4, то есть час), потом помечается `unreachable` и раскатку не держит.
  Станция, загрузившая выпуск (ACK OK) или ушедшая на испытание, но не подтвердившая его за
  `ZS_ROLLOUT_CONFIRM_TIMEOUT_S` (2 часа), помечается так же. Это не отказ: такую станцию можно повторить следующей
  раскаткой;
- станция, у которой heartbeat уже показывает выпуск (или новее), команды не получает (`already`); ответ
  `REJECTED 4` (версия не новее) при таком heartbeat — тоже `already`, без него — отказ;
- `skip` выводит станцию из раскатки (ожидающую или ту, которую раскатка ждёт);
- `cancel` снимает ожидающие станции (`skipped`); станции в полёте доводятся до конца и остаются в журнале;
- `completed` — когда ни одна станция не ожидает и не в полёте.

Состояния станции в раскатке: `pending → commanded → installed (ACK OK) → trial → confirmed`; конечные — `confirmed`,
`already`, `skipped`, `failed`, `rolled_back`, `unreachable`. Состояния раскатки: `canary`, `running`, `paused`,
`completed`, `cancelled`.

Раскатку двигает исполнитель в процессе сервера раз в `ZS_ROLLOUT_TICK_S` (30 с; `0` — только стенд): читает ACK и
heartbeat, которые сохранили мосты, переводит станции и ставит команды следующим. Команды — обычные строки
`commands`, мосты публикуют их как любые другие (аддендум D); станция в один момент может быть только в одной
активной или остановленной раскатке.

## 2. Возврат

Станция отказывает выпуску, который не новее работающего (аддендум F §3, `REJECTED 4`; §6: защита от отката только
этим правилом), поэтому «откатить командой на прежнюю версию» нельзя. `revert` делает то, что возможно: отменяет
раскатку и начинает новую — с *возвратным выпуском*: прежний образ, подписанный заново под версией выше возвращаемой
(`python -m pki.cli fw-sign` с образом прежней сборки, собранной с большим `ZS_FW_VERSION_CODE`), — для всех
станций, которым раскатка успела скомандовать. Без такого выпуска в хранилище `revert` отвечает отказом и объясняет,
что нужно. Откат самой станции (страж после трёх неудачных стартов, heartbeat `ROLLED_BACK`) раскатка видит и
записывает как отказ `rolled_back`.

## 3. Журнал

Каждая раскатка ведёт свой журнал (`rollout_journal`): создание (кто, выпуск, станции, canary, пределы), каждая
команда станции (идентификатор команды, попытка, с какой версии), каждый ACK, каждый heartbeat, сдвинувший станцию
(испытание, подтверждение, откат), прохождение canary-волны, паузы с причиной (автоматические — от `runner`),
продолжения, пропуски, отмены, возвраты (с идентификатором возвратной раскатки — и в ней ссылка назад) и завершение
со счётом по состояниям. Журнал отдаётся вместе с раскаткой (`GET /api/v1/firmware/rollouts/{id}`), срокам хранения
не подлежит. Запросы инженера, которые всё это сделали, записаны и в журнале действий учётных записей
(`docs/SERVER_ACCESS_CONTROL_2026-10-02.md`): кто, откуда, что, ответ.

## 4. API

Права: все `POST` — `station.firmware` (роль `engineer`), чтение — `read`. Учётная запись с ограничением по участкам
и станциям видит раскатки, затрагивающие её станции, и может создать раскатку только на видимые станции.

```
POST /api/v1/firmware/rollouts            {"version": 7, "stations": [17,18,19,20], "canary": [17],
                                           "max_failures": 1, "max_in_flight": 10}     -> раскатка
GET  /api/v1/firmware/rollouts                                                         -> список со счётом состояний
GET  /api/v1/firmware/rollouts/{id}                                                    -> станции и журнал
POST /api/v1/firmware/rollouts/{id}/pause   {"reason": "..."}
POST /api/v1/firmware/rollouts/{id}/resume
POST /api/v1/firmware/rollouts/{id}/cancel  {"reason": "..."}
POST /api/v1/firmware/rollouts/{id}/revert  {"version": 8, "reason": "..."}            -> возвратная раскатка
POST /api/v1/firmware/rollouts/{id}/stations/{station_id}/skip {"reason": "..."}
GET  /api/v1/health                                                                    -> rollouts: настройки, последний проход
```

Вместо `canary` можно дать `canary_count` (0 — без canary-волны). Ответы 409 — отказы правил (выпуска нет в
хранилище, станция уже в другой раскатке, возвратный выпуск не новее), 404 — раскатка или станция не видна.

## 5. Проверка

`server/tests/test_rollout.py` (6 проверок): canary → основная волна по две в полёте → завершение, порядок журнала;
отказ по ACK → автопауза → `resume` → `skip` canary-станции → основная волна → откат станции (heartbeat
ROLLED_BACK) → пауза снова → `cancel` с доведением станции в полёте; `already` по heartbeat и по `REJECTED 4`,
повтор команды после TTL и `unreachable`, таймаут подтверждения; `revert` — отказ на версию не новее и на выпуск,
которого нет, возвратная раскатка на скомандованные станции, ссылки в журналах; правила создания и настройки из
окружения; маршруты оператора через приложение, 404/409/422, права `station.firmware` на каждый `POST`.
Станционная сторона (загрузка, испытание, подтверждение, откат стражем) проверена сценариями 6/6b двойника
(`server/tools/test_station_twin_e2e.py`).

## 6. Что осталось

- Раскатка на двойниках поля (три станции, настоящие сессии) — после того как `tools/twin_field.py` научится
  принимать команды сервера; станционная сторона OTA на двойнике уже проходит сценарии 6/6b.
- Страница раскаток в веб-интерфейсе: сегодня обновление прошивок и раскатки — только API (как и до этого
  обновление одной станции); на странице станции показывать `fw_version / fw_state` и раскатку, в которой она.
- Пакеты модели (аддендум I) идут той же командой; раскатка волнами для них делается тем же исполнителем с
  хранилищем моделей — отдельным шагом.
