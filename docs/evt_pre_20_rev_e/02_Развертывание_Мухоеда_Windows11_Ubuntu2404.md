# Развертывание сервера Мухоед

Редакция: Rev E от 06.10.2026.

## 1. Выбор платформы

Ubuntu Server 24.04 LTS рекомендуется для VPS и постоянно работающего выделенного сервера. Windows 11 подходит для стенда, демонстрации и локального сервера при использовании Docker Desktop с WSL2. Производственный сервер должен иметь постоянное доменное имя, корректное время, резервное копирование и HTTPS.

| Параметр | Минимум EVT | Рекомендуется |
|---|---|---|
| CPU | 4 ядра x86-64 | 8 ядер |
| RAM | 8 ГБ | 16 ГБ |
| Диск | 100 ГБ SSD | 250 ГБ NVMe и отдельное резервное хранилище |
| Сеть | Публичный HTTPS и MQTT/TLS 8883 | Статический адрес, DNS, мониторинг |
| ОС | Windows 11 или Ubuntu 24.04 LTS | Ubuntu 24.04 LTS |

## 2. Получение релиза

Проверить SHA-256 серверного архива по манифесту. Распаковать в отдельный каталог. Закрытые ключи и `.env` не берут из поставочного архива: их создают на сервере или переносят из защищенного хранилища по утвержденной процедуре.

## 3. Ubuntu Server 24.04 LTS

### 3.1. Подготовка

1. Установить обновления безопасности, Docker Engine и Compose plugin.
2. Создать служебный каталог `/opt/muhoed/server` и каталог резервных копий вне него.
3. Создать DNS A/AAAA для сервера и проверить синхронизацию времени.
4. Разрешить входящие 443/tcp и 8883/tcp. Порт 8000 оставить только на localhost.
5. Скопировать серверный архив и сверить его SHA-256.

### 3.2. Конфигурация

Скопировать `deploy/.env.example` в `deploy/.env`. Установить сильные уникальные значения. Производство не должно содержать `ZS_STATION_HTTP_INSECURE_BENCH=1`, `ZS_OPERATOR_AUTH_INSECURE_BENCH=1`, `ZS_OPERATOR_COOKIE_SECURE=0` или `ZS_OPERATOR_TOTP=0`.

Разместить TLS и командные ключи в каталогах, указанных compose. Закрытый command signing key должен иметь права 0600. Сертификат MQTT должен содержать публичное имя и DNS-имя сервиса `mqtt`.

### 3.3. Запуск

В каталоге `server/deploy` проверить конфигурацию командой `docker compose -f compose.ubuntu.yml config`. Затем собрать и запустить `docker compose -f compose.ubuntu.yml up -d --build`. Проверить `/api/v1/health`, страницу `/login`, порт 8883 и список контейнеров.

Настроить reverse proxy с HTTPS. Он обязан передавать исходный Host, Origin, WebSocket Upgrade и X-Forwarded-For. Включить автоматическое обновление публичного сертификата и уведомление до его истечения.

## 4. Windows 11

### 4.1. Подготовка

1. Включить аппаратную виртуализацию и WSL2.
2. Установить Docker Desktop и выбрать Linux containers.
3. Разрешить Docker использовать минимум 8 ГБ RAM и 4 CPU.
4. Распаковать сервер в каталог без синхронизации OneDrive.
5. Хранить рабочие данные в именованном томе или отдельном локальном каталоге NTFS.

### 4.2. Стендовый запуск

Для изолированного стенда допустим `deploy/compose.windows.yml`. Он содержит упрощенный режим и не используется как публичный боевой сервер. Для TLS применяют `deploy/compose.windows.tls.yml`, собственный `.env`, сертификаты и закрытый командный ключ с ограниченным NTFS ACL.

### 4.3. Публичный Windows-сервер

Публичное размещение на Windows требует отдельного reverse proxy, автоматического HTTPS, запрета внешнего доступа к 8000, регулярных резервных копий, автозапуска Docker Desktop после перезагрузки и операционного мониторинга. После обновления Windows проверяют WSL2, Docker, время, health, HTTPS, MQTT/TLS и вход оператора.

## 5. Первичная настройка доступа

До публикации сервера войти как `skif_root`, заменить временный пароль и привязать второй фактор. Затем создать отдельные учетные записи дежурных, инженеров и администраторов. Общие учетные записи не используют. Для каждой учетной записи задают только необходимые станции и tenants.

## 6. PKI и станции

Root CA выпускается offline. На сервере создается запрос issuing CA, который подписывается Root CA. После установки цепочки выпускаются сертификаты сервера, bridge и станций. Для каждой станции сервер принимает CSR, подписывает его и формирует защищенный station package. Реестр, ACL и CRL сохраняются и резервируются.

## 7. Изолированный bench

Контур цифровых двойников запускается отдельным compose-проектом `dioneya-bench` из `deploy/compose.bench.yml`. Он использует отдельные базу, MQTT, TLS, учетные записи и порты 127.0.0.1:8001 и 127.0.0.1:8884. Идентификаторы двойников: 9001 - 9040. Нельзя монтировать производственные `data`, `tls`, operator state или command signing key в bench.

## 8. Резервное копирование и восстановление

На Ubuntu применять `deploy/scripts/backup_ubuntu.sh`. На Windows применять `deploy/backup_windows.ps1`. Скрипты создают согласованную копию SQLite через API базы. Нельзя копировать работающий файл SQLite без WAL. Восстановление проводят только после проверки архива и с автоматическим сохранением заменяемого состояния.

Минимальный график: ежедневная копия данных, еженедельная проверка восстановления на отдельном стенде, ежемесячная копия PKI-реестра и CRL, хранение минимум трех поколений.

## 9. Обновление

1. Зафиксировать текущий BUILD_ID и создать резервную копию.
2. Проверить SHA-256 нового серверного архива.
3. Проверить `docker compose config` и выполнить регрессию на bench.
4. Собрать новые образы, перезапустить только производственные сервисы.
5. Проверить health, login, stations, replay, WebSocket, MQTT/TLS, журнал и свободный диск.
6. Если проверка не пройдена, восстановить предыдущий архив и базу по процедуре rollback.

## 10. Контроль после запуска

- `/login` отвечает по HTTPS.
- `/api/v1/health` возвращает status ok, версию и BUILD_ID.
- Неавторизованный пользователь получает отказ на рабочих страницах.
- Контейнеры server, mqtt, bridges и mqtt_alerts работают.
- Страница «Станции» показывает возраст heartbeat и версию.
- Событие тревоги переводит оператора на «Сопровождение».
- Резервная копия создается и проходит проверку целостности.
- Bench доступен только локально или через контролируемый SSH-туннель.

## 11. Особенности текущего dioneya.ru

Боевой контур использует HTTPS и MQTT/TLS 8883. Отдельный проект `dioneya-bench` использует локальные 8001 и 8884. Производственные и тестовые данные разделены. Перед каждым обновлением проверяют, что старый контейнер bench из производственного compose не запущен и что рабочий bench относится к проекту `dioneya-bench`.
