# Выпуск сертификатов и регистрация станций Дионея

Редакция: Rev E от 06.10.2026.

## 1. Роли PKI

Root CA работает только на offline-компьютере. Issuing CA находится в защищенном контуре сервера. EOL-оператор создает CSR и переносит подписанный сертификат на конкретную станцию. Один station package нельзя применять к двум изделиям.

## 2. Типы секретов

| Материал | Где хранится | В общий архив не входит |
|---|---|---|
| Root CA private key | Offline носитель | Да |
| Issuing CA private key | Защищенный сервер PKI | Да |
| Station private key | Устройство или защищенный EOL | Да |
| Pairing secret | Реестр PKI, этикетка, устройство | Да |
| Command signing private key | Сервер bridge | Да |
| Firmware/model release private key | Offline signing workstation | Да |
| Android release keystore | Защищенный signing workstation | Да |

## 3. Первичная PKI

1. На offline-компьютере выполнить `python -m pki.offline_tool root-init` на защищенный носитель.
2. На сервере выполнить `python -m pki.cli issuing-request`.
3. Перенести только CSR issuing CA на offline-компьютер и подписать командой `issuing-sign`.
4. Установить issuing certificate и root certificate командой `issuing-install`.
5. Выпустить MQTT server certificate с публичным DNS, DNS `mqtt` и IP сервера.
6. Выпустить отдельные bridge certificates для pilot1, pilot2 и bench.

## 4. Реестр изделий

Полевые изделия имеют серийные номера DIO-EVT-001 - DIO-EVT-040. Стендовое изделие: DIO-EVT-B01. Двойники имеют числовые ID 9001 - 9040 и не получают производственные идентичности. Перед выдачей сертификата сверить серийный номер платы, корпуса, реестр партии и этикетку.

## 5. CSR станции

Предпочтительно генерировать закрытый ключ внутри устройства и извлекать только CSR. До аппаратного подтверждения допускается EOL fixture, которое генерирует ключ в защищенном рабочем каталоге и удаляет его после успешной записи и проверки.

Команда EOL-инструмента формирует CSR с CN, равным серийному номеру. Перед подписью проверить CN, открытый ключ, партию и отсутствие активного сертификата с тем же серийным номером.

## 6. Подпись и station package

На сервере выполнить регистрацию партии, затем `station-sign <serial> --csr <file>`. После этого сформировать bundle и station package. Текущая версия station package содержит сертификат, цепочку CA, сетевые параметры, pairing secret и необходимые публичные ключи. Пакет имеет ограниченные права и не должен выводиться в журнал или мессенджер.

## 7. Загрузка в станцию

1. Проверить SHA-256 station package.
2. Перевести станцию в сервисный режим.
3. Записать serial и pairing secret до первого защищенного BLE-сеанса.
4. Загрузить station certificate, private key и CA chain в BG95 по процедуре EOL.
5. Записать публичные command и release keys в целевой компонент.
6. Выполнить холодный старт и проверить наличие файлов в модеме.
7. Проверить mTLS к dioneya.ru:8883 и появление heartbeat на сервере.

## 8. ACL и CRL

После добавления станции пересоздать `station_acl.conf` командой `mosquitto-acl`, применить его к broker и проверить, что станция может работать только со своими topics. CRL обновлять до истечения и после каждого отзыва.

## 9. Этикетка и pairing secret

Создать QR командой `label-qr`, проверить печать и читаемость приложением монтажника. Pairing secret уникален, не является общим паролем партии и не публикуется. При потере этикетки выполнить `pairing-secret-rotate`, обновить устройство, реестр и этикетку.

## 10. Отзыв и замена

При утрате станции или подозрении на компрометацию отозвать сертификат, обновить CRL и ACL, перезапустить MQTT и подтвердить отказ старого сертификата. Новую идентичность выпускать с записью причины и ссылкой на старый serial. Закрытый ключ не восстанавливают из резервной копии общего назначения.

## 11. Evidence

Для каждого изделия сохраняются serial, lot, SHA-256 CSR, серийный номер сертификата, срок, SHA-256 station package, оператор, дата, результат загрузки, результат mTLS и server receipt. Закрытый ключ и pairing secret в обычный отчет не записываются.
