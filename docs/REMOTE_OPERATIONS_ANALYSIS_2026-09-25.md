# Удалённое управление станцией: что объективно нужно (2026-09-25)

Исходные данные: пилот 41 станция (2 лота + стенд), выезд на точку дорогой; станция онлайн только в S3
(после события, по heartbeat раз в 6 ч, при outbox-retry/GSM-пробе); команды подписаны Ed25519, TTL ≤ 15 мин,
идемпотентны через журнал; сейчас ICD определяет одну команду — `CMD_REQUEST_AUDIO`.

## Находки важнее команд

1. **Нет аппаратного сторожевого таймера (IWDG).** Зависшая станция (дедлок задач, зависание HAL/SPI/UART)
   мертва до выезда — и никакая команда её не спасёт: она не выйдет на связь. Это P0, без протокола.
   Нужен IWDG с проверкой живости задач (супервизор кормит IWDG, только если все критичные задачи отметились)
   и причина сброса в heartbeat, чтобы сервер видел «станция перезагрузилась по watchdog, виновата задача X».
2. **Команды мертвы без GNSS-времени.** Проверка TTL требует доверенного времени; без фикса GNSS (антенна,
   установка в помещении, отказ модуля) станция отвергает *все* команды (`TIME_UNTRUSTED`), включая ту, что
   могла бы её починить. Нужен резервный источник времени с пониженным доверием для команд — время сети
   (BG95 NITZ `AT+QLTS`) внутри mTLS-сессии; для TTL 15 мин точности в секунды достаточно. На привязку событий
   это не влияет (там остаётся PPS).
3. **`REQUEST_AUDIO` почти всегда опоздает.** После публикации события S3 завершается, как только outbox пуст;
   оператор запросит аудио через минуты — команда дойдёт в следующую сессию (до 6 ч), а кольцо предыстории
   в NOR (~65 мин) к тому времени перезапишется. Решение из двух частей: (а) при событии станция замораживает
   pre/post в слот архива события (`zs_archive`, 3 слота — уже есть как модуль, `AudioReference.local_slot`);
   (б) сервер по политике сам ставит `REQUEST_AUDIO` для CONFIRMED-событий сразу по приёму события — команда
   успевает в ту же сессию; станция держит сессию `linger` ≈ 60 с после события, чтобы её принять.

## Команды: нужны / не нужны

| Команда | Нужна? | Почему |
|---|---|---|
| `CMD_REQUEST_AUDIO` (1) | да, есть в ICD | проверка срабатываний и ложных тревог; без неё классификатор не улучшить по данным пилота |
| `CMD_REBOOT` (2) | да, дёшево | восстановление «живой, но деградировавшей» станции: NOR ушёл в RAM-фолбэк, модем в странном состоянии, DSP-перегрузка; ACK до сброса, повтор после сброса не перезагружает второй раз (журнал `COMPLETED`) |
| `CMD_SET_PARAMS` (3) | да | подстройка под площадку без выезда — главная операционная работа с акустическими детекторами: канал микрофона (обход отказавшего микрофона), период обновления события, период heartbeat, пороги деградации GSM, период GSM-пробы, dwell прослушивания. Только белый список параметров с диапазонами, «сброс к умолчаниям», хранение в NOR, хеш в heartbeat |
| ротация ключа команд | да, позже | ICD обещает ротацию подписанной командой; при компрометации серверного ключа иначе — выезд на все 41 станцию. Отдельный дизайн: нельзя отозвать ключ, которым подписана команда; всегда ≥ 1 активный |
| сетевая конфигурация (хост, APN) | позже | полезно при переезде сервера, но может «окирпичить» связь; только с пробным применением и автооткатом по неудачной сессии (A/B-слоты конфигурации уже есть) |
| обновление прошивки STM32 (OTA) | да, отдельный трек | самая ценная удалённая функция для пилота и самая крупная: загрузчик A/B, подпись образа, докачка по MQTT; не команда, а подсистема |
| «запросить heartbeat сейчас» | нет | команду станция получает только онлайн — heartbeat в этой сессии уйдёт и так |
| «открыть сервисное окно BLE» | нет | BLE — для работы на месте; удалённое открытие расширяет поверхность атаки без пользы (на месте есть TAMPER 5 с) |

## Порядок реализации
1. IWDG + живость задач + причина сброса в heartbeat (P0).
2. Резервное время для команд (NITZ, пониженное доверие).
3. ICD-аддендум C: `CMD_REBOOT`, `CMD_SET_PARAMS`; кодеки станция/сервер с векторами; исполнитель на станции.
4. Аудио: архив события (слоты), выгрузка (аддендум B), linger, серверная авто-политика.
5. Ротация ключа; сетевая конфигурация с автооткатом; OTA — отдельными треками.
