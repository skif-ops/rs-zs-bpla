# Цифровые двойники станций Дионея на стенде Мухоеда

Эта инструкция задаёт три ступени проверки связки «станция — Мухоед»: 3, 20 и 40 виртуальных станций. Рабочие станции участков `pilot1` и `pilot2` продолжают работать со своей базой. Испытательный контур `bench` получает отдельные MQTT-брокер, PKI, базу, аудиофайлы, учетные записи, сеть и процессы сервера. Стенд размещается в отдельном каталоге `/opt/muhoed-bench/server` на том же VPS; его порты `127.0.0.1:8884` и `127.0.0.1:8001` доступны только с самого VPS или через SSH-туннель. Производственный Compose-проект, MQTT-брокер и реестр не изменяются.

## Что уже проверяется локально

| Ступень | Модель | Проверка |
| --- | --- | --- |
| 3 | `server/tools/twin_field.py`: три отдельных процесса переносимой прошивки | Обнаружение одной цели, сердцебиение, пеленги, слияние, отчёт испытания |
| 20 | `server/tools/load_field.py --stations 20 --tenant bench --station-id-base 9000` | Путь MQTT-моста внутри процесса, повторы QoS 1, связь после обрыва, сбор событий и нагрузки |
| 40 | Та же программа с `--stations 40` | Нагрузка полной партии, восстановление после обрывов и перезапуска моста |

Нагрузочная программа вызывает код моста непосредственно и записывает отдельную SQLite-базу. Она **не** подтверждает реальный радиоканал, TLS, брокер Mosquitto или сетевую задержку. Для ступеней 20 и 40 это имитаторы сообщений станций, а не 40 запущенных экземпляров прошивки.

Для проверки трёх процессов прошивки используется `tools/twin_field.py` после сборки `zs_station_twin`:

```text
python tools/twin_field.py --out <results>/firmware-3 --station 9001:0,0 --station 9002:1200,0 --station 9003:600,1000 --target=-2500,2200,200,45,-10,0 --seconds 180
```

Следующие команды проверяют нагрузочный имитатор для 3, 20 и 40 станций. Запускать их из каталога `server`, с отдельным каталогом результатов вне `server/data`:

```text
python tools/load_field.py --stations 3  --tenant bench --station-id-base 9000 --hours 2  --out <results>/3  --check
python tools/load_field.py --stations 20 --tenant bench --station-id-base 9000 --hours 2  --out <results>/20 --check
python tools/load_field.py --stations 40 --tenant bench --station-id-base 9000 --hours 24 --out <results>/40 --check
```

В показанных командах используются ID 9001…9040, которые не пересекаются с 1…40 физических станций и действующим образцом 901. В интерфейсе они обозначены «Двойник 01»…«Двойник 40», серийные номера `DIO-TWIN-001`…`DIO-TWIN-040`. Перед выдачей сертификатов повторно проверить живой реестр; при совпадении ID остановить подготовку и изменить карту ID в коде и документации. Результат нагрузочной ступени находится в `report.json` рядом с отдельной базой. Успех означает `ok: true`, отсутствие сообщений без подтверждения и ошибок обработки, полное сохранение уникальных событий, пеленгов и аудио.

После выполнения защитных шагов ниже проверить настоящий TLS-брокер, мост и хранилище стенда. `tools/bench_mqtt_twins.py` проверяет все сертификаты до отправки, допускает только 3, 20 или 40 ID в tenant `bench`, требует явный флаг `--execute` и отправляет не чаще одного heartbeat в секунду. Без флага трафик не отправляется:

```text
python tools/bench_mqtt_twins.py --stations 3 --credentials <bench-credentials> --ca <ca-chain.pem> --out <results>/mqtt-3.json
python tools/bench_mqtt_twins.py --stations 3 --credentials <bench-credentials> --ca <ca-chain.pem> --out <results>/mqtt-3.json --execute
python tools/bench_mqtt_twins.py --stations 20 --credentials <bench-credentials> --ca <ca-chain.pem> --out <results>/mqtt-20.json --execute
python tools/bench_mqtt_twins.py --stations 40 --credentials <bench-credentials> --ca <ca-chain.pem> --out <results>/mqtt-40.json --execute
```

Сетевая ступень подтверждает MQTT PUBACK каждой станции; после неё отдельно сверить 3/20/40 актуальных heartbeat в изолированной базе и отсутствие новых ID в рабочей базе. Пеленги, звук и алгоритмы дополнительно проверяет локальный `load_field.py`, который не посылает данные в рабочий брокер.

## Как изолируется bench на сервере

`server/deploy/compose.bench.yml` запускается из отдельного исходного каталога и задаёт Compose-проект `dioneya-bench`. Брокер, сервер и мост получают свою сеть и тома, сертификаты лежат в `/opt/muhoed-bench/config/tls`, реестр и сообщения в `/opt/muhoed-bench/server/data`. `twin_sender` отправляет по одному синтетическому heartbeat на станцию раз в 30 минут; он ограничен 0,25 CPU и 128 MiB памяти. Сервис публикации alert для bench включается только отдельным профилем `alerts`. Рабочий Compose-проект `deploy` не подключается к этой сети. Новые виртуальные ID видны только в интерфейсе bench после настройки отдельной учётной записи; старые данные bench в рабочей базе, если они были созданы ранее, остаются историческими. Прежний общий профиль `bench` в `compose.ubuntu.yml` не использовать для новых двойников.

Перед первым сетевым запуском:

1. Сверить фактическую конфигурацию dioneya.ru с этой веткой, проверить свободные локальные порты и запас ресурсов. Зафиксировать число записей и максимальный ID в рабочем реестре до прогона.
2. Создать **новую** PKI только для bench. Корневой закрытый ключ хранить вне VPS. Выпустить серверный сертификат с SAN `mqtt` и `localhost`, сертификат клиента `bridge-bench`, ключ подписи команд bench. Установить только необходимые ключи в `/opt/muhoed-bench/config/tls`.
3. Зарегистрировать серийные номера `DIO-TWIN-001`…`DIO-TWIN-040` в PKI bench (ID 9001…9040, tenant `bench`) и выпустить для них отдельные сертификаты. Эти записи не входят в стандартную партию 41 изделия и не попадают в рабочий реестр. Не использовать сертификаты и ID физических станций.
4. Реестр PKI bench уже содержит только двойников; монтировать его в `server/data/pki` испытательного проекта. Сформировать отдельный ACL и проверить, что каждому сертификату станции разрешены только её темы `zs/v1/bench/<id>/…`. Сертификат `bridge-bench` не имеет доступа к `pilot1` и `pilot2`.
5. До запуска сервера создать отдельную учётную запись и заменить начальный пароль `skif_root` через CLI `station.operator_auth`. Проверить `docker compose -f deploy/compose.bench.yml config`, затем включить сервисы в отдельном проекте. Производственный Compose-файл не применять.
6. Проверить, что `127.0.0.1:8001` показывает только 40 двойников, а рабочая страница `/stations` не показывает ID 9001…9040. Проверить отсутствие тестовых событий и новых ID в рабочей базе.
7. Подавать трафик последовательно: 3, затем 20, затем 40. При росте задержки рабочих heartbeat, переполнении диска, ошибках MQTT или влиянии на рабочие оповещения сразу остановить испытание.

Остаётся общий VPS. Лимиты CPU и памяти bench-контейнеров снижают риск; перед сетевым прогоном нужен замер запаса ресурсов и ограничение скорости отправителя. В случае ухудшения рабочих метрик остановить только Compose-проект `dioneya-bench`.

## Интерфейс состояния станций

Страница `/stations` теперь начинает с карточек состояния; каждая открывает соответствующую строку подробной таблицы. Счётчики и карточки можно ограничить участком, `bench` обозначен как «испытания». Таблица сохранена для инженерного разбора heartbeat, а доступ к данным по-прежнему задаётся серверной областью видимости оператора. Обновление происходит раз в минуту; ошибка обновления показана отдельно от времени последнего успешного ответа.
