# Цифровые двойники станций Дионея на стенде Мухоеда

Эта инструкция задаёт три ступени проверки связки «станция — Мухоед»: 3, 20 и 40 виртуальных станций. Рабочие станции участков `pilot1` и `pilot2` продолжают работать со своей базой. Испытательный контур `bench` получает отдельные базу, аудиофайлы, учетные записи и процессы сервера; MQTT-темы отделены именем tenant. Изменения подготовлены для проверки и не означают, что новая конфигурация уже развернута на dioneya.ru.

## Что уже проверяется локально

| Ступень | Модель | Проверка |
| --- | --- | --- |
| 3 | `server/tools/twin_field.py`: три отдельных процесса переносимой прошивки | Обнаружение одной цели, сердцебиение, пеленги, слияние, отчёт испытания |
| 20 | `server/tools/load_field.py --stations 20 --tenant bench --station-id-base 1000` | Путь MQTT-моста внутри процесса, повторы QoS 1, связь после обрыва, сбор событий и нагрузки |
| 40 | Та же программа с `--stations 40` | Нагрузка полной партии, восстановление после обрывов и перезапуска моста |

Нагрузочная программа вызывает код моста непосредственно и записывает отдельную SQLite-базу. Она **не** подтверждает реальный радиоканал, TLS, брокер Mosquitto или сетевую задержку. Для ступеней 20 и 40 это имитаторы сообщений станций, а не 40 запущенных экземпляров прошивки.

Для проверки трёх процессов прошивки используется `tools/twin_field.py` после сборки `zs_station_twin`:

```text
python tools/twin_field.py --out <results>/firmware-3 --station 1001:0,0 --station 1002:1200,0 --station 1003:600,1000 --target=-2500,2200,200,45,-10,0 --seconds 180
```

Следующие команды проверяют нагрузочный имитатор для 3, 20 и 40 станций. Запускать их из каталога `server`, с отдельным каталогом результатов вне `server/data`:

```text
python tools/load_field.py --stations 3  --tenant bench --station-id-base 1000 --hours 2  --out <results>/3  --check
python tools/load_field.py --stations 20 --tenant bench --station-id-base 1000 --hours 2  --out <results>/20 --check
python tools/load_field.py --stations 40 --tenant bench --station-id-base 1000 --hours 24 --out <results>/40 --check
```

В показанных командах используются ID 1001…1040, которые не пересекаются с 1…40 физических станций и действующим образцом 901. Перед выдачей сертификатов повторно проверить живой реестр; при совпадении ID остановить подготовку и изменить карту ID в коде и документации. Результат нагрузочной ступени находится в `report.json` рядом с отдельной базой. Успех означает `ok: true`, отсутствие сообщений без подтверждения и ошибок обработки, полное сохранение уникальных событий, пеленгов и аудио.

После выполнения защитных шагов ниже проверить настоящий TLS-брокер, мост и хранилище стенда. `tools/bench_mqtt_twins.py` проверяет все сертификаты до отправки, допускает только 3, 20 или 40 ID в tenant `bench`, требует явный флаг `--execute` и отправляет не чаще одного heartbeat в секунду. Без флага трафик не отправляется:

```text
python tools/bench_mqtt_twins.py --stations 3 --credentials <bench-credentials> --ca <ca-chain.pem> --out <results>/mqtt-3.json
python tools/bench_mqtt_twins.py --stations 3 --credentials <bench-credentials> --ca <ca-chain.pem> --out <results>/mqtt-3.json --execute
python tools/bench_mqtt_twins.py --stations 20 --credentials <bench-credentials> --ca <ca-chain.pem> --out <results>/mqtt-20.json --execute
python tools/bench_mqtt_twins.py --stations 40 --credentials <bench-credentials> --ca <ca-chain.pem> --out <results>/mqtt-40.json --execute
```

Сетевая ступень подтверждает MQTT PUBACK каждой станции; после неё отдельно сверить 3/20/40 актуальных heartbeat в изолированной базе и отсутствие новых ID в рабочей базе. Пеленги, звук и алгоритмы дополнительно проверяет локальный `load_field.py`, который не посылает данные в рабочий брокер.

## Как изолируется bench на сервере

В `server/deploy/compose.ubuntu.yml` сервер `bench_server`, мост `mqtt_bridge_bench` и издатель `mqtt_alerts_bench` используют только `server/bench-data`, а результаты bench лежат в `server/bench-output`. Эти каталоги находятся вне рабочей резервной копии. Рабочие сервер, мосты `pilot1` и `pilot2` и их издатель используют `server/data`. Рабочий издатель исключает `bench`, сохраняя публикацию для остальных рабочих участков; издатель bench имеет отдельный MQTT client ID и публикует только `dioneya/alert/v1/bench`. Испытательные процессы получают отдельный сертификат `bridge-bench`, у которого брокер разрешает только темы `bench`, и отдельный ключ подписи команд. Профиль Compose `bench` выключен по умолчанию. Веб-интерфейс bench привязан к `127.0.0.1:8001` для локального SSH-туннеля; публичный маршрут к нему не настроен. Новые виртуальные ID видны только в интерфейсе bench после настройки отдельной учётной записи; старые данные bench в рабочей базе, если они были созданы ранее, остаются историческими.

Перед первым сетевым запуском:

1. Сверить фактическую конфигурацию dioneya.ru с этой веткой и сделать резервную копию рабочей базы. Убедиться, что мост `bench` монтирует только `server/bench-data`.
2. Выпустить отдельный сертификат MQTT: `python -m pki.cli bridge-cert --cn bridge-bench --pki <pki>`; установить `bridge-bench.crt.pem` и `bridge-bench.key.pem` в `server/deploy/tls`. Сгенерировать отдельную пару ключей команд `command-signing-bench.key` и `command-signing-bench.pub` через `tools/generate_command_signing_key.py`. Не копировать рабочий закрытый ключ в испытательные контейнеры.
3. Зарегистрировать серийные номера `DIO-TWIN-001`…`DIO-TWIN-040` в рабочем PKI (ID 1001…1040, tenant `bench`) и выпустить для них отдельные сертификаты. Эти записи не входят в стандартную партию 41 изделия и по умолчанию скрыты из рабочего каталога и мониторинга. Не использовать сертификаты и ID физических станций. Записать открытый ключ команд bench в конфигурацию каждого двойника.
4. Создать отдельный реестр для интерфейса bench командой `python -m pki.bench_export --source server/data/pki/registry.sqlite3 --out server/bench-data/pki/registry.sqlite3`. Экспорт переносит только общедоступные метаданные bench и не переносит записи физических станций, ключи сопряжения и инженерные ключи. После добавления или отзыва двойника повторить экспорт и перезапустить `bench_server`.
5. Перегенерировать ACL брокера из живого PKI и проверить права пользователя `bridge-bench`. Применить ACL сигналом SIGHUP процессу Mosquitto без перезапуска контейнера, затем проверить сохранение рабочих соединений. Проверить, что MQTT ACL виртуальной станции разрешает только её собственные темы `zs/v1/bench/<id>/…`, а сертификат `bridge-bench` и клиент испытаний не имеют права писать в `pilot1` или `pilot2`.
6. Включить сервисы только явной командой `docker compose --profile bench up -d` после проверки конфигурации, отдельной учётной записи bench и резервной копии. Проверить, что через локальный адрес `127.0.0.1:8001` доступны только данные bench, а рабочая страница `/stations` не показывает новые виртуальные ID. Проверить отсутствие test-событий в рабочем `dioneya/alert/v1/pilot1` и `…/pilot2`.
7. Подавать трафик последовательно: 3, затем 20, затем 40. При росте задержки рабочих heartbeat, переполнении диска, ошибках MQTT или влиянии на рабочие оповещения сразу остановить испытание.

Общий брокер и хост всё ещё делят ресурсы. Лимиты CPU и памяти bench-контейнеров снижают риск, но перед сетевым прогоном нужен замер запаса на VPS и ограничение скорости отправителя. Пока отдельные сертификаты, ACL и сетевой отправитель не подготовлены и не проверены, допустимы только локальные прогоны.

## Интерфейс состояния станций

Страница `/stations` теперь начинает с карточек состояния; каждая открывает соответствующую строку подробной таблицы. Счётчики и карточки можно ограничить участком, `bench` обозначен как «испытания». Таблица сохранена для инженерного разбора heartbeat, а доступ к данным по-прежнему задаётся серверной областью видимости оператора. Обновление происходит раз в минуту; ошибка обновления показана отдельно от времени последнего успешного ответа.
