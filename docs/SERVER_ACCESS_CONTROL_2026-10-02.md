# Сервер: роли, права, второй фактор, сессии и журнал аудита (2026-10-02, этап 1)

Код: `server/station/operator_auth.py`. Проверки: `server/tests/test_operator_auth.py`, QG-1
`tools/validate_operator_auth.py`, QG-2 `tools/audit_operator_auth_technical.py`. Руководство по развёртыванию:
`server/deploy/README.md`.

## 1. Роли и права

Роль — набор прав. У учётной записи может быть несколько ролей; права складываются.

| Право | Что разрешает | Наблюдатель | Оператор | Инженер | Администратор безопасности | Сервисная |
|---|---|:-:|:-:|:-:|:-:|:-:|
| `read` | страницы, карта, события, станции, треки, поток событий | + | + | + | + | + |
| `audio.listen` | звук событий (может содержать речь) | | + | + | | |
| `audio.request` | запрос звука у станции | | + | + | | |
| `analysis.run` | разбор одного файла, локализация | | + | + | | |
| `dataset.edit` | добавление, обучение, удаление в наборе данных | | | + | | |
| `station.command` | сетевая конфигурация станций | | | + | | |
| `station.firmware` | обновление прошивки и модели | | | + | | |
| `scopes.manage` | какие участки и станции видит учётная запись | | | + | + | |
| `keys.rotate` | смена ключа подписи команд | | | | + | |
| `users.manage` | учётные записи | | | | + | |
| `audit.read` | журнал аудита | | | | + | |

Администратор безопасности не командует станциями, инженер не управляет учётными записями и ключом команд: одна
скомпрометированная учётная запись не даёт и того и другого.

Каждый изменяющий маршрут приложения назван в таблице правил (`PERMISSION_RULES`). Маршрут, которого там нет,
отклоняется для всех (`unmapped`), пока его не объявят; тест `test_every_changing_route_is_declared` и QG-2
проверяют это для всех маршрутов, которые регистрирует приложение, включая будущие.

Файл учётных записей прежнего вида (`"role": "operator"` / `"viewer"`) работает без правки: оператор остаётся
оператором и входит без второго фактора, никто не теряет доступ при обновлении. Права инженера (набор данных,
команды станциям) прежние операторы теперь получают явно: `set-roles <имя> --roles operator,engineer` и
`totp-enroll <имя>`.

## 2. Второй фактор

Инженер и администратор входят с кодом TOTP (RFC 6238: HMAC-SHA1, 30 с, 6 цифр) из приложения-аутентификатора;
сеть для этого не нужна. `totp-enroll` выдаёт секрет один раз (строкой и ссылкой `otpauth://`). Без секрета такая
учётная запись не входит. Код принимается в своём 30-секундном шаге и в соседних (расхождение часов) и только один
раз: повторно предъявленный код отклоняется. Неверный код считается неудачной попыткой входа (общая блокировка
5/20 попыток на 15 минут). `ZS_OPERATOR_TOTP=0` выключает требование только на стенде; QG-1 проверяет, что в
production compose этой переменной нет.

## 3. Сессии

Cookie (HttpOnly, SameSite=Strict, Secure, HMAC-подпись) несёт только номер сессии и версию пароля; сама сессия
хранится на сервере (`data/operator_state.sqlite3`, режим 0600). Сессию завершают: выход (повтор старого cookie
после выхода отклоняется), 30 минут без запросов, 12 часов с входа, смена пароля, отключение (`disable`) и удаление
учётной записи, `logout-all`. Роли и права читаются из файла учётных записей на каждом запросе: изменение роли
действует сразу.

## 4. API-токены

Токен скрипта получает права (`--scopes`, по умолчанию `read`) и никогда не больше, чем у его учётной записи;
может иметь срок (`--expires-days`). Токены прежнего вида (без scopes) сохраняют права своей учётной записи.

## 5. Журнал аудита

Записываются: входы, неудачные входы (с причиной: пароль, код, блокировка, нет второго фактора), выходы, каждый
изменяющий запрос (кто, откуда, метод и путь, код ответа, токен), отказы по правам, каждое действие CLI с учётными
записями. Каждая запись содержит SHA-256 предыдущей; `audit-verify` находит изменённую или удалённую запись
(кроме удаления хвоста журнала: от этого защищает резервная копия). Чтение (GET) не записывается.

## 6. Участки и станции

`set-scope <имя> --tenants north --stations 17,18` задаёт, что видит учётная запись (пусто — всё). Значения
доходят до каждого запроса (`request.state.operator`: `tenants`, `stations`, `roles`, `permissions`). Применение
во всех API данных и в потоке событий — этап B (следующее изменение); веб-панель администратора — этап 2.

## 7. Что осталось

- Этап B: фильтр станций и участков в каждом API данных, в потоке событий и в выходном API тревог; назначение
  видимости инженером и администратором.
- Этап 2: страница `/admin` (учётные записи, роли, видимость, токены, сессии, журнал) поверх тех же функций, с
  повторным вводом кода второго фактора для опасных действий.
- Проверки на целевом сервере (пункт 1 аудита выпуска остаётся открытым до них).
